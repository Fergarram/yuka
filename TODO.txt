
I am basically at a pretty good point when it comes to canvas controls. It feels great currently, for both trackpad and mouse. It could even be great for keyboard users only with the setup I have now.

GOALS:

[ ] Share this build with others so I can test design.
[ ] Eventually, test an MCP to give control to assistants.
    The scripts' command buffer (lua::Cmd) and frame snapshot are the natural surface: an
    MCP or IPC socket could parse into the same commands and read the same snapshot.
[x] Modability: the part of this system that behaves like a game engine or video game
    Rust is the engine and lua/ (LuaJIT, hot reloaded) defines the experience: bindings,
    gestures, camera, focus, placement, animations, window looks and shaders, overlays.

BUGS:

[ ] The idle finger on buttons area should not trigger in the middle of other gestures like the 3 finger swipe
[ ] It seems that some new windows or sub-surfaces or whatever from a window parent render as new window using the nearest empty space thing
[ ] Sometimes moving cursor near edges or corners doesn't really show the resize thing. We should handle that ourselves because it sucks.
[x] 3-finger double tap, when it focuses a window it should not move it up the z index
[ ] Un-maximizing puts a window back about 32px off from where it was, with every client
    (weston, ghostty, ...). The restore rect is taken from the visible top-left, and the
    client changes its geometry offset (drops its shadow) while maximized, so the origin
    is restored against the wrong offset. Predates the Lua move.
[ ] Some context menus appear out of screen so we need to make sure they appear inside.
[ ] When FPS drop, it drops for everyone which I guess is expected... but i thnk the mouse drawing should not be affected by it?

IMPROVEMENTS OR TESTS:

[ ] When window in focus and NOT maximized. If super is pressed and cursor on top of this window, two-finger pinch should resize the window from center and we should use the pinch aspect ratio as a way to set the new size proportion as well.

[ ] Palm rest. I think done by increasing the minimum area required to mark as finger depending on how close to the sides it is.

[x] Render texts in raylib with a way fucking nicer font like IBM Plex mono and make it so that we never scale that shit or change the font size.

[ ] State that survives a reload. Not settings (those stay in lua/), but what the scripts
    change while running: the night range, a theme switched with looks.set_theme, the
    layout picked. A reload starts a fresh VM, so today all of it falls back to what the
    files say. The engine could keep a small store (string keys, plain values) that Lua
    reads and writes through yk.*, kept across reloads and maybe written to disk so it
    also survives a restart.

[ ] Expose as much of raylib to Lua as we can. The idea is to be able to build a whole game living inside yuka, in Lua only. Each fn is one line in ray.rs and one in the yk_fns! macro in src/lua.rs; loaded resources get id handles owned by the VM, like yk.font.
    - 2D draw: rounded rects, thick lines, circle/ellipse outlines and fills, triangles, polygons, rings, arcs, gradients, scissor, blend modes.
    - Textures: images and textures from files, DrawTexturePro, render textures for offscreen drawing.
    - Text: the rest of rtext (codepoint drawing, line spacing, text in a rect).
    - Shaders: custom shaders and uniforms on 2D and 3D drawing, sharing the window shader slots or alongside them.
    - 3D: Camera3D, shapes, models and meshes, materials, drawn in yk.draw.
    - Audio: init the device, sounds, music streams, volume and pitch.
    - Input for games: probably through the snapshot rather than raylib's input, since the engine owns input.
    Keep a script from crashing the compositor: check every handle and size, nothing raw reaches Lua.

    Needs the KMS loop to be ours: raylib's DRM platform is one connector, one
    CRTC, one blocking modeset per frame, so two screens means owning the flips
    (atomic commit per CRTC, page flip events, a wl_output each, hotplug on udev
    change events). Then a decision the canvas has to answer: are two monitors two
    viewports into one canvas, so a window crosses the bezel, or two independent
    cameras.
    The flip work exists in git stash (see commit d0e6ae4): it measured a 12ms
    latency cut and felt worse three times, but item 2 alone was never tested on
    its own. Worth checking whether the old per-frame modeset was presenting
    immediately, i.e. tearing, since that would explain the feel and would make
    vsync versus async flips a deliberate per-output switch rather than a
    regression.
